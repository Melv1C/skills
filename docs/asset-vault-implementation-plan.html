1. Verdict

The starter is already ~60% of the platform you want (Hono, Better Auth, Prisma/Postgres, React+Vite, TanStack Router/Query, shadcn/ui, Docker, Dokploy-oriented CI). It is ~0% of the product: no Asset model, no object storage, no API keys, no OpenAPI, no asset UI.

Strategy: evolve in place. Do not greenfield a new monorepo. Rename later if desired; ship features first under apps/backend and apps/frontend.

What works today

  • Hono app mounts /api, CORS to frontend, request IDs, Prometheus /metrics, Winston (+ optional Loki).
  • Better Auth: email/password, Prisma adapter, admin plugin. Handler at /api/auth/*.
  • Auth middleware sets user/session; helpers isAuthenticated / isAdmin.
  • Health route under /api/health.
  • Frontend: QueryClient, router, root layout, placeholder home page, auth client with admin + genericOAuth plugins.
  • Dockerfiles for backend (Bun) and frontend (nginx static). Turbo prune for builds.
  • Varlock env schemas shared via .env.shared.

What does not exist yet

  • Any Asset / permission / metadata tables
  • MinIO or S3 client / storage interface
  • Better Auth apiKey + bearer plugins
  • OpenAPI / Scalar docs
  • Multipart upload routes or public /a/:id
  • Login / assets / settings UI routes
  • Shared packages/db or api-client

4. Keep / adapt / skip

Keep as-is

  • Bun + Turbo monorepo
  • Varlock env generation
  • Prisma in apps/backend (no packages/db yet)
  • packages/ui component library
  • Prometheus + logger plumbing
  • Existing auth User/Session/Account/Verification models
  • App names backend / frontend for now

Adapt deliberately

  • Auth: add apiKey + bearer; optionally Better Auth openAPI plugin for auth docs
  • Middleware: resolve session or API key into the same user context
  • Compose: add MinIO + create default bucket on boot
  • Env URLs: plan path toward same-origin (assets.example.com) later; keep split URLs in development
  • Frontend auth client: drop unused genericOAuthClient unless OAuth is in v1
Skip for v1 packages/api-client, packages/db extraction, Redis, queues, MCP, GraphQL, CLI, CDN, permissions table (owner-only first), expiresAt enforcement job, multi-tenant orgs.

5. Decisions locked now

Core noun is Asset, not File/Image
Schema, routes, and UI all say Asset. Content-type stays a field; future subtypes do not require a rename.
Postgres = metadata; object storage = bytes
Never store binary in Postgres. storageKey is the only link to the object.
Public delivery goes through Hono (/a/:id)
Bucket stays private. Hono authorizes, then streams or redirects to a short-lived signed URL. CDN can sit in front later without changing clients.
HTTP API is the primary interface; OpenAPI from day one
Agents get /api/docs. Humans and curl use the same contract. No CLI in v1.
Auth ownership split
Better Auth owns users, sessions, accounts, verification, API keys. App owns Asset (+ later permissions/metadata).
v1 authorization is owner-only
No asset_permissions table yet. Visibility is private | public. Private requires owner (session or API key). Public is readable via /a/:id without auth.
Storage interface now; MinIO first
Implement Storage with put/get/delete/exists/createPresignedUrl. Ship MinIO driver. S3/R2 are config swaps later.
IDs
Use ULID (or UUIDv7) for Asset.id so public URLs are opaque and sortable. Prefer ULID for the agent-friendly 01K… shape from the product sketch.

6. Data + auth model

Better Auth (existing + extend)

User ──< Session
  │
  ├──< Account
  ├──< Verification
  └──< Apikey   (plugin tables; exact names from Better Auth generate)

Asset.ownerId → User.id

Asset (new)

model Asset {
  id          String    @id          // ULID
  ownerId     String
  owner       User      @relation(...)
  filename    String
  contentType String
  size        BigInt
  sha256      String
  storageKey  String    @unique
  visibility  Visibility @default(PRIVATE)
  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt
  expiresAt   DateTime?

  @@index([ownerId, createdAt])
  @@map("asset")
}

enum Visibility {
  PRIVATE
  PUBLIC
}
Invariant storageKey is internal (e.g. assets/{ownerId}/{id}). Clients never see or guess bucket paths; they only ever use Asset id and /a/:id.

Deferred tables

  • AssetPermission (share with other users / scoped keys)
  • AssetMetadata (JSON key/value or typed fields)
  • Soft-delete / retention audit log

9. Implementation phases

Phase 0 — Align foundations

0.5–1 day
  • Confirm product name / env hostnames (replace leftover vo2.melvyn.be placeholders when ready).
  • Add MinIO to docker-compose.yml; document bun run docker:db → rename script to docker:deps or similar.
  • Add S3 env vars to backend .env.schema; generate types.
  • Decide ULID library (ulid or similar) and max upload size.

Phase 1 — Auth model for agents

1 day
  • Enable Better Auth apiKey + bearer plugins; regenerate Prisma schema via Better Auth CLI; migrate.
  • Update useAuth so Bearer API keys resolve to the same user as cookie sessions.
  • Mirror client plugins; keep email/password for humans.
  • Smoke: create key via API, call a protected stub with Authorization: Bearer ….

Phase 2 — OpenAPI skeleton

0.5–1 day
  • Introduce @hono/zod-openapi (or Hono OpenAPI helper already compatible with Zod 4 in this repo) for app routes.
  • Mount Scalar at /api/docs; serve OpenAPI JSON.
  • Document auth schemes: cookie session + HTTP bearer.
  • Keep Better Auth routes outside the OpenAPI app router if needed; link to them from docs intro text.

Phase 3 — Storage + Asset core

2–3 days
  • Implement Storage interface + S3/MinIO driver.
  • Add Asset Prisma model + migration.
  • Services: assets.ts (create/list/get/update/delete) composing prisma + storage + sha256.
  • Routes: full CRUD under /api/assets with OpenAPI schemas; multipart upload.
  • Route: GET /a/:id with public/private checks.
  • Return url + markdown on create.
  • Manual test with curl using API token (the killer workflow).

Phase 4 — Token management surface

0.5–1 day
  • Expose list/create/revoke under /api/tokens (wrappers over Better Auth API key APIs if needed).
  • Document one-time secret display rule.

Phase 5 — Web UI

2–3 days
  • Auth gate: /login; redirect unauthenticated users.
  • /assets: list, upload, visibility badge, copy URL / markdown.
  • /assets/$id: detail, rename, visibility toggle, delete.
  • /settings/tokens: create/revoke keys.
  • Use existing @repo/ui primitives; boring dashboard is fine.
  • TanStack Query hooks for assets/tokens only talking to /api.

Phase 6 — Packaging & deploy

1–2 days
  • Dev: one compose stack with postgres + minio; api/web still via bun run dev (or optional compose services).
  • Prod: Dokploy compose/project with api + web + postgres + minio (all-in-one first); document split-storage option.
  • Ensure bucket is private; only Hono public path is reachable.
  • Smoke staging: upload via curl with token; open URL; revoke in UI.

11. Explicitly out of v1

  • Redis, Kafka, queues, Elasticsearch, K8s, microservices
  • Dedicated worker / expiry sweeper (store expiresAt, enforce later)
  • CLI, MCP server, GraphQL
  • Separate auth service
  • Cross-user sharing / ACL table
  • Image transforms, virus scan, multipart resumable uploads
  • CDN (design allows it; do not configure yet)

12. Definition of done (v1)

  1. Human can register/login in the web UI and upload an asset.
  2. Human can create an API token and revoke it.
  3. Agent can upload with: 
    curl -X POST "$BASE/api/assets" \
  -H "Authorization: Bearer $ASSET_TOKEN" \
  -F "file=@screenshot.png" \
  -F "visibility=public"
    and receive url + markdown.
  4. Public URL /a/:id works without auth; private returns 401/403 without owner credentials.
  5. Owner can change visibility or delete; public URL stops working after delete.
  6. /api/docs documents the asset and token endpoints.
  7. docker compose up brings up Postgres + MinIO; local bun run dev runs api + web against them.
Suggested next design pass (before coding Phase 3) Lock exact OpenAPI schemas for Asset create/list responses, error envelope, pagination, max upload size, and whether GET /a/:id redirects or streams. That is the last high-leverage design work before implementation.
