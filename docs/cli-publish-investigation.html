A small CLI for Skills auth and publishing

The shortest useful path is a thin command-line client around the API that already exists. Let auth login accept an API token, validate it, and store it locally. Upload assets and HTML with native web APIs, then print the returned URL.

Recommendation: build v1 One runtime dependency: Commander Token login with secure local storage
Decision. Build a single package with five focused auth and publishing commands: auth login, auth status, auth logout, plus asset upload and document publish. Let login receive a token from a hidden prompt or an environment variable. Use Commander for parsing and help, the runtime's built-in fetch, FormData, Blob, and filesystem APIs for transport, and support --json for automation.

What exists today

The deployed API is already a good CLI boundary. It accepts API keys in either Authorization: Bearer av_... or x-api-key. The live health check and authenticated asset and document list checks both returned successfully during this investigation.

Capability Current API CLI implication
Check authentication GET /api/assets requires auth Use as a cheap authenticated probe; do not print the key.
Upload media POST /api/assets, multipart file, optional visibility and filename Return url and markdown.
Publish HTML POST /api/documents, multipart file, optional clientKey, description, visibility, forceNew Return the stable document URL. A repeated key appends a version.
Replace a document PUT /api/documents/:id Optional explicit update command; v1 can rely on clientKey.
Manage keys GET/POST/DELETE /api/tokens; creation is session-authenticated Keep key creation in the dashboard for v1.
Important current behavior. Documents default to public, but newly created assets default to private in the backend. Hosted HTML and shared reports need public assets, so asset upload should default to public and expose an explicit private option.

Use explicit nouns and verbs. Avoid a broad deploy command, project manifests, recursive directory uploads, or a local cache until real usage demonstrates a need for them.

Minimal options

Option Purpose Default
--base-url <url> Override the API for staging or local development. https://api.skills.melvyn.be
--allow-insecure-http Allow an HTTP base URL only when it points to loopback development. Off.
--visibility <value> Set public or private visibility without an interactive question. Public for assets and documents.
--filename <name> Override the server display name. Local basename.
--description <text> Set document metadata. Unset.
--key <key> Make document publishing repeatable and versioned. Unset, which creates a new document.
--force-new Detach the key from the previous document and create a fresh one. Off.
--json Print the complete API response for scripts. Human-readable URL summary.

Auth: pass and store an API token

The existing API-key flow is enough for the CLI. auth login should accept a token, validate it against an authenticated endpoint, and store the token in a user-level file with restrictive permissions. No password or Better Auth session cookie is needed. 

agent-tools auth login
Paste your token: ...

agent-tools auth login
Already connected

agent-tools auth login --force
Paste your token: ...
  1. With no stored token, auth login shows a hidden Paste your token: prompt, validates the token, and stores it only after authentication succeeds.
  2. With a valid stored token, it validates the token and prints Already connected without prompting.
  3. With an invalid stored token, it reports Stored token is invalid and suggests agent-tools auth login --force instead of silently replacing credentials.
  4. With --force, always prompt for a replacement token and atomically overwrite the stored value only after validation succeeds.
  5. Run agent-tools auth status or agent-tools auth check to validate the stored token. Run agent-tools auth logout to remove the local copy.

The CLI can still honor SKILLS_API_TOKEN directly for CI and agents without storing it. Local logout removes the stored copy only and does not revoke the remote API key. Remote creation and revocation remain in the dashboard for v1.

Implementation shape

One small package

Add one CLI package to the existing workspace. Its public executable should be exposed through the package's bin field. Keep API DTOs local to the client until a shared public API package is actually needed.

One API helper

Centralize base URL resolution, auth headers, multipart requests, JSON error parsing, status handling, and output formatting. Commands should mostly validate arguments, read a file, call the helper, and print.

Native multipart

Read bytes from disk, create a Blob with the detected MIME type, append it to FormData, and let fetch set the multipart boundary. No upload SDK is required.

Small token store

Keep a single JSON file under the user's config directory, create its directory with mode 0700, and write the file with mode 0600. Remove it on logout. Do not store passwords. A stored API token is a secret and must never be logged.

Illustrative request logic

const form = new FormData();
form.append("file", new Blob([await readFile(file)], { type }), basename(file));
form.append("visibility", visibility);
if (key) form.append("clientKey", key);

const response = await fetch(`${baseUrl}/api/documents`, {
  method: "POST",
  headers: { Authorization: `Bearer ${token}` },
  body: form,
});

The server remains the source of truth for HTML policy, maximum size, hashing, title extraction, and document versioning. Duplicating those checks in the CLI would make the client larger and create drift.

Commander is a good fit

Commander covers subcommands, positional arguments, options, help generation, and usage errors in a small, familiar API. That is enough structure for this command surface, and it avoids writing and maintaining a custom argument parser. Keep it as the only CLI-specific dependency.

Reference: Commander.js README. For executable packaging and the workspace's existing runtime, see Bun package executables and Bun runtime documentation.

Failure and safety rules

  • Missing auth: explain that agent-tools auth login or SKILLS_API_TOKEN is required and exit non-zero.
  • 401: say the token is missing, invalid, expired, or revoked. Never echo it.
  • 400: print the API's safe error and validation details, if present.
  • 413: tell the user which limit was exceeded. Do not retry unchanged bytes.
  • 500 or network timeout: show status and request ID when supplied. Do not automatically retry uploads, because asset creation is not idempotent.
  • Use public visibility when a URL will be embedded in hosted HTML. A private asset cannot be fetched by readers without the API key.
  • Do not put the token in command arguments. Arguments can leak through shell history and process listings; use the hidden prompt or SKILLS_API_TOKEN instead.

Phased delivery

  1. Prototype: add the package, Commander, shared API helper, token login/logout, auth status, and the two upload commands.
  2. Confidence: add fetch-mocked tests and run the commands against a staging base URL with a disposable key.
  3. Distribution: build JavaScript for Node 20+, publish the package, and document installation plus the one required environment variable.
  4. Skill integration: simplify the asset and HTML skill instructions to prefer the CLI for local files, while retaining curl as the fallback and debugging path.
  5. Later: add list, delete, explicit document updates, remote token lifecycle commands, and Better Auth session login only when usage warrants them.
Bottom line. The MVP is still mostly client packaging and request plumbing. A token-based auth login is simpler than a password session flow: accept the token safely, validate it, store it securely, and reuse it for uploads. Commander keeps the command tree clean; no upload library, generated SDK, or backend redesign is necessary.
